# 需求梳理：设计风格方向选择器（Style Lock-in）

> 版本：v0.1 需求草案  
> 状态：待评审  
> 一句话定位：**先锁定视觉方向，再进入实现。**  
> 核心交付物：**可复用的 Style Spec，而不是一张好看的图。**

---

## 1. 背景与问题

在用 AI 把想法做成产品时，常见路径是：一句话需求或一张线框 → 直接生成高保真界面或代码。结果往往是：

- 每一轮生成的视觉气质都不一样，无法形成稳定方向
- 图本身好看，但和原始想法、目标用户、使用场景对不上
- 选中一张图之后，下一页、下一个组件、下一次对话又重新“抽卡”
- 和设计师、外包、开发对齐时，只能说“高级一点 / 简洁一点”，无法给出可执行的视觉约束

根因不是“生成能力不够”，而是 **结构（做什么）和风格（长什么样）被绑在同一次生成里**，且选完之后没有把风格固化成资产。

用户提出的原始想法是对的：根据原型图或需求描述生成多张图，让用户挑选。但只做到“出图 + 挑选”还不够——必须把挑选结果变成后续所有生成和开发都遵守的风格规格。

---

## 2. 产品定位

### 2.1 这是什么

一个 **设计方向决策层**，夹在“想法/原型”和“真正出稿/出代码”之间。

```
想法 / 原型图 / 需求描述
        ↓
  风格候选生成与挑选     ← 本产品主战场
        ↓
  Style Spec 锁定
        ↓
  后续页面生成 / Figma / v0 / Cursor / 人工设计
```

### 2.2 这不是什么

| 不是 | 原因 |
| --- | --- |
| 又一个文生图工具 | Midjourney / Firefly 已经做得很好，但选完图无法稳定复用到产品 |
| 一句话出完整 App | v0 / Lovable / Bolt / Stitch 已覆盖，痛点正是风格不可控 |
| 完整设计工具或设计系统平台 | Figma 的事，MVP 不做编辑器 |
| 竞品界面仿制器 | 可从参考图抽 token，但禁止像素级抄袭 |

### 2.3 两层问题必须同时写进需求

- **层 A · 找风格**：发散，给用户看多个可视化方向
- **层 B · 锁风格**：收敛，形成可复用资产，防止后续漂移

用户原话只覆盖了层 A。能真正解决问题的是层 B。

---

## 3. 目标用户

按痛感和付费意愿排序：

1. **独立开发者 / vibe coding 用户**（MVP 第一优先）  
   用 v0、Lovable、Cursor、Claude 做产品。最大痛点：每轮生成都不像上一轮。
2. **产品经理 / 创始人（非设计背景）**  
   有 PRD、草图或墨刀线框，说不清风格，和设计师/外包沟通成本高。
3. **设计师**  
   用于快速给甲方看选项，但他们已有 Figma，不是 MVP 主力。
4. **甲方 / 业务方**  
   适合当“选风格会”的道具，不是日常用户。

MVP 先打 1 + 2，不要先做设计师工作台。

---

## 4. 核心使用场景

### 场景 1：独立开发者准备用 AI 做 App

- 前置：一句话需求，或一张低保真线框
- 动作：生成 4–6 个“同一结构、不同气质”的首页方向，单选或融合
- 后置：导出 Style Spec / CSS tokens / prompt pack，贴进 v0 或 Cursor 继续做全站

### 场景 2：PM 要和设计师或外包对齐视觉方向

- 前置：PRD + 手绘 / 墨刀 / 即时设计线框
- 动作：开会时并排看 4–6 个方向，当场锁定
- 后置：输出风格说明书，减少“做出来不像我想的”

### 场景 3：有参考图，但不确定要不要照搬

- 前置：1–3 张竞品截图或情绪板 + 自己的原型
- 动作：生成“像参考但不复制”的变体
- 后置：抽取 token，避免直接抄竞品视觉

### 场景 4：风格已锁，但下一页又漂了

- 前置：已有 Style Card
- 动作：新页面强制绑定同一张卡，只变布局不变气质
- 后置：多页面一致性检查

### 场景 5：觉得“还行但不对”，不想推倒重来

- 前置：已选风格 A
- 动作：按维度微调（更克制 / 更暖 / 更密 / 更圆）
- 后置：生成 A2，保留 A 可回退

## 5. 端到端主流程

```
1. 输入
   原型图 和/或 文字需求 和/或 参考图
        ↓
2. 解析（对用户半可见）
   结构层：页面类型、区域、组件、阅读顺序
   意图层：品类、受众、平台、情绪、禁忌
   冲突时：结构以原型图为准，风格以文字约束为准
        ↓
3. 确认槽位（可跳过，但建议保留）
   “这是一个面向年轻用户的健身 App 首页，对吗？”
        ↓
4. 第一轮生成：4 个差异够大的方向
   同一布局骨架 × 不同风格象限
        ↓
5. 挑选
   单选锁定 / 勾选 2 张融合 / 按维度微调
        ↓
6. 第二轮（可选）：同一方向的近似变体
   深浅、密度、对比度、圆角微调
        ↓
7. 锁定前确认卡（10 秒）
   关键词 + 色板 + 组件气质 + 反例（这个风格不适合什么）
        ↓
8. 输出 Style Spec
   Style Card（给人看）+ Tokens（给机器）+ Prompt Pack（给后续 AI）
        ↓
9. 应用
   用同一 style_id 生成第 2 个页面做一致性抽检
   导出到 Figma variables / CSS / Tailwind / 下游 AI 工具
```

关键交互原则：

- 主界面是 **同布局多风格网格对比**（4 宫格），不要左右滑
- 风格判断需要并排对照，滑动会丢掉比较基准
- 第一轮必须差异够大，避免 4 张都是“蓝紫渐变玻璃拟态”
- 可加三问打分：贴近想法 / 视觉喜欢 / 可落地，避免“图好看但不是我想要的”

## 6. 输入规范

### 6.1 三种输入，允许混合

| 输入 | 作用 | 优先级 |
| --- | --- | --- |
| 原型图（线框、手绘、截图、墨刀导出） | 锁定结构：信息架构、组件类型、布局 | 结构层最高 |
| 文字需求（一句话到短 PRD） | 锁定意图：品类、受众、情绪、禁忌 | 风格约束最高 |
| 参考图 / 网址（可选） | 提供风格线索，不是结构来源 | 仅影响风格轴 |

混合规则：

- 图为主、文字为辅是默认路径
- 结构冲突时以原型图为准
- 风格冲突时以用户文字为准（用户说了“极简商务”，就不能跟着参考图走赛博风）
- 缺信息时生成待确认清单，不要默默脑补品牌色

### 6.2 原型图的常见卡点与对策

| 卡点 | 对策 |
| --- | --- |
| 手绘/低清，阴影和透视干扰 | 引导“拍清晰、尽量俯视、少阴影”；草图走 scribble/Canny 预处理 |
| 按钮、列表、图表分不清 | 允许用户点选区域，标注组件类型 |
| 一次丢多页原型 | 先选 1 张旗舰页定风格，再批量套到其他页 |
| 竞品截图和自己的线框混在一起 | 明确区分“结构参考”和“风格参考”两个上传槽 |
| 只有文字没有图 | 先给 3 个布局骨架让用户点选，再套风格 |
| 形容词含糊（高级一点、好看一点） | 翻译成可视化滑杆：对比度、圆角、留白、饱和度 |

### 6.3 解析后的统一中间表示

所有输入最终合并为一份 Generation Spec：

```json
{
  "structure": {
    "page_type": "app_home",
    "device": "mobile",
    "regions": ["header", "hero", "stats", "list", "tabbar"],
    "components": ["avatar", "search", "primary_cta", "card_list"]
  },
  "intent": {
    "category": "fitness",
    "audience": "young_urban",
    "mood": ["energetic", "clean"],
    "must_have": ["today_training", "streak"],
    "forbidden": ["game-like", "neon"]
  },
  "constraints": {
    "brand_colors": [],
    "must_dark": false
  }
}
```

后续所有风格变体都吃这一份 spec，而不是各自重新理解原文。

## 7. 风格体系

不要让模型自由采样。风格空间用正交轴描述，每一批候选覆盖不同象限。

### 7.1 正交轴（生成时强制拉开距离）

| 轴 | 取值 | 用户可感知的说法 |
| --- | --- | --- |
| 明暗 | light / dark | 浅色清爽 / 深色沉浸 |
| 密度 | airy / comfortable / dense | 留白多 / 适中 / 信息密 |
| 几何 | sharp / rounded / soft | 直角克制 / 圆角亲和 / 很圆很软 |
| 气质 | minimal / editorial / playful / enterprise / luxury | 极简 / 杂志感 / 活泼 / 企业 / 高端 |
| 材质 | flat / glass / tactile | 扁平 / 玻璃拟态 / 有触感 |

同一批候选禁止：同一主色、同一字体族、同一圆角等级。

### 7.2 MVP 预设方向（第一轮默认 4 选）

系统根据品类和意图，从下列方向里挑 4 个差异最大的，而不是固定死 4 个模板：

1. 极简留白 Minimal
2. 商务稳重 Enterprise / 瑞士国际主义
3. 年轻活泼 Playful / Soft UI
4. 高级质感 Luxury / Editorial
5. 科技深色 Dark Tech
6. 玻璃拟态 Glassmorphism
7. 新拟态 Neumorphism（慎用，对比度差，适合特定品类）
8. 粗野主义 Brutalism（适合内容/工具产品，不适合金融主路径）
9. 新中式 / 国风现代（有明确文化诉求时）
10. 赛博朋克 / 强氛围（仅娱乐、游戏、活动向）

默认不出 7–10，除非意图层明确匹配。金融、医疗、政务默认落在 1、2、5。

### 7.3 每张候选旁要展示的解读

避免用户只凭“好不好看”做决定。每张图旁边固定给出：

- 这张在表达什么（一句话气质）
- 它可能偏离需求的哪一点
- 适合什么产品，不适合什么产品
- 三个可落地特征：主色倾向、圆角等级、信息密度

锁定前再加一张 10 秒确认卡：风格关键词 + 色板 + 组件气质 + 反例。

## 8. 生成策略：结构与风格解耦

这是本需求和技术方案的中心原则。

### 8.1 不要做什么

- 不要把原图和原文直接丢给同一个文生图模型
- 不要每张候选都重新构图
- 不要用“请保持同样风格”这种软提示防漂移

### 8.2 推荐双轨

| 轨道 | 作用 | 特点 |
| --- | --- | --- |
| Token 主题渲染 | 可复用、可开发的候选 | 先出布局骨架（线框或组件树），再套不同 theme token 渲染预览 |
| 图像模型氛围图 | 帮助用户感受气质 | 低 denoise 的 layout-preserving style transfer，或 ControlNet/Canny 锁结构 |

用户挑的是方向，落地用 token。纯生图可以作为“感受”，不能作为唯一交付。

### 8.3 挑选后的三种操作

1. **单选锁定**：该候选的 token + prompt pack 成为 style_id
2. **双选融合**：色板取 A、几何取 B、气质取更靠近用户文字的一侧，再生成 2 张融合结果供确认
3. **维度微调**：只改被点名的轴（更干净、更暖、更圆、更密、更品牌化），其他轴保持，生成 A2，A 可回退

禁止：根据新一轮自然语言全量重写 Style Spec。

---

## 9. 锁定后产物（真正的交付物）

选完图后必须同时落下三件套，缺一不可。

### 9.1 Style Card（给人看、给会议看）

- 风格名 + 一句话气质
- 代表色 6–8 个（主色、辅色、背景、表面、文字、边框、成功/危险）
- 字体方向（标题 / 正文，不承诺具体商用字体时可给开源替代）
- 圆角等级、阴影等级、间距密度
- 组件气质：按钮是实心还是线框，卡片是描边还是浮起，输入框是盒子还是下划线
- Do / Don't
- 反例：这个风格不适合什么

### 9.2 Design Tokens（给机器、给开发）

兼容 W3C DTCG 思路，至少包含：

- color：bg / surface / text / muted / primary / accent / danger / border
- typography：family、size scale、weight、lineHeight
- radius、spacing、shadow、density
- component vibes：button、card、input

同时导出：

- JSON tokens
- CSS variables
- Tailwind theme 片段
- Figma variables 可导入格式

### 9.3 Style Spec 最小 schema（锁定后必须落库）

```json
{
  "style_id": "sty_xxx",
  "rev": 1,
  "meta": {
    "name": "冷静商务",
    "one_liner": "浅色、克制、适合 B 端工具",
    "source": ["prototype", "text"],
    "locked_from": ["candidate_03"]
  },
  "intent": {
    "product_type": "saas_dashboard",
    "audience": "企业管理者",
    "platform": "web",
    "mood": ["calm", "trustworthy"],
    "forbidden": ["neon", "playful-illustration", "heavy-gradient"]
  },
  "tokens": {
    "color": {
      "bg": "#F7F8FA",
      "surface": "#FFFFFF",
      "text": "#1F2937",
      "muted": "#6B7280",
      "primary": "#2563EB",
      "accent": "#0EA5E9",
      "danger": "#DC2626",
      "border": "#E5E7EB"
    },
    "typography": {
      "family_ui": "Inter",
      "family_display": "Inter",
      "scale": [12, 14, 16, 20, 24, 32],
      "weight_body": 400,
      "weight_title": 600
    },
    "shape": { "radius_sm": 6, "radius_md": 10, "radius_lg": 16 },
    "elevation": "subtle-border",
    "density": "comfortable",
    "motion": "short-fade"
  },
  "component_vibe": {
    "button": "filled-primary",
    "card": "outlined",
    "nav": "left-sidebar-light",
    "input": "box"
  },
  "prompt_pack": {
    "positive": "clean enterprise SaaS, light gray canvas, blue accent, generous whitespace",
    "negative": "cyberpunk, neon, skeuomorphism, cluttered widgets"
  }
}
```

### 9.4 Prompt Pack（给后续 AI 生成）

- 正向风格描述
- 负向约束（negative constraints）
- 结构锁说明：只换皮肤，不改信息架构
- 绑定 seed / style embedding / 参考缩略图
- 版本号：`style_id + rev`

下游约定：v0 / Lovable / Cursor / 自研生成器读取 tokens + prompt pack；多页面生成全部 bind 同一个 style_id。

## 10. 与竞品的差异

| 产品 | 擅长 | 缺口 | 和本需求的关系 |
| --- | --- | --- | --- |
| Midjourney / Firefly | 出好看的图、情绪板 | 不懂页面结构，选完无法复用到产品 | 可借鉴“并排变体”交互，不借鉴交付物 |
| Uizard / Visily / Balsamiq AI | 草图/截图转可编辑线框 | 风格体系弱，主任务是结构还原 | 可作为上游输入源 |
| Figma Make / Figma AI | 在已有画布上出高保真 | 前提是已经在 Figma 里工作 | 下游衔接，不是替代 |
| Google Stitch / Galileo | 文本/草图出完整 UI | 风格选择是附带的 | 直接出成品，容易跳过决策 |
| UX Pilot | 同线框出多种高保真风格，可接设计系统 | 更偏设计工具，锁定资产不够一等公民 | 最接近的交互参考 |
| Relume | 营销站 sitemap + wireframe + style guide | 偏站点组件库，不是任意产品原型 | Style Guide → Design View 的“先锁再铺”可借鉴 |
| Mowgli | 先出 4 个旗舰页方向，选完再铺全站 | 仍是完整设计工具 | 主流程最像，可直接对标 |
| v0 / Lovable / Bolt | 直接出可运行代码 | 风格不可控，正是上游缺口 | 本产品的下游客户 |
| VisualSnag 等 token 抽取工具 | 已有参考图抽 token | 没有参考时无法先探索 | 只覆盖“已有风格”半边 |

差异化一句话：

> 竞品多是“直接出成品”。我们是“先做风格决策层，再把决策喂给成品生成”。

## 11. 功能需求与范围

### 11.1 功能清单

P0（MVP 必做）

- F1 文字需求输入与槽位抽取（品类 / 受众 / 平台 / 情绪 / 禁忌）
- F2 原型图上传与结构解析（线框 / 草图 / 截图）
- F3 同结构多风格候选生成（默认 4 张，正交轴）
- F4 并排挑选：单选锁定 / 双选融合
- F5 维度微调（明暗、冷暖、圆角、密度、对比）
- F6 输出 Style Card + Tokens + Prompt Pack
- F7 风格锁定后的二次预览（至少再出 1 个不同页面做一致性抽检）

P1

- F8 多页原型：指定旗舰页定风格，其余页只套用
- F9 参考图与结构图分离上传
- F10 导出 CSS variables / JSON tokens / 下游 prompt
- F11 风格版本与回退

P2

- F12 下游一键喂给 v0 / Cursor / Figma
- F13 品牌约束模式（已有色 / Logo 不准乱改）
- F14 多页面一致性检查报告

### 11.2 明确不做

- 不直接替代 Figma 做精细设计
- 不保证生成图可直接开发（图是决策界面，token 才是资产）
- 不提供像素级复制某竞品 App
- 不做完整多页应用生成、设计系统管理、自动写生产代码
- 不用左右滑动选风格

## 12. 风险与约束

### 12.1 版权与品牌

- 用户上传竞品截图时：只允许抽取 token（色、字号倾向、圆角、密度），禁止像素级复刻某品牌界面
- 生成图标记来源类型：原创探索 / 参考启发
- 字体只推荐开源或可商用列表（Inter、Source Han、IBM Plex 等），商用字体只作“方向描述”
- 已有品牌资产时走约束模式，token 变更必须出 diff，不能静默改

### 12.2 多轮漂移（最大产品风险）

对策：

- 结构通道和风格通道分离，微调只改被点名的轴
- 每次迭代对比锁定 token 的 delta，超阈值警告
- 用锁定预览页做回归：同一 hero / form / list 三块必须视觉可对齐
- 禁止“根据新一轮自然语言全量重写 style spec”
- 成功标准对用户可见：选完后下一屏仍是同一套 token

### 12.3 可落地性

- 图好看不等于组件可实现
- MVP 就必须同时出 token，否则选完无法进开发
- 新拟态、强玻璃拟态、赛博风要标注“实现成本 / 无障碍风险”
- 对比度不达标的候选要降权或打警告

### 12.4 选择疲劳

- 第一轮默认 4 张，不要一上来 8 张
- 4 张必须落在不同象限
- 第二轮才出近似变体

## 13. 成功指标

产品指标，不是模型分数：

| 指标 | 目标（MVP） | 含义 |
| --- | --- | --- |
| 首次锁定时长 | ≤ 3 分钟 | 从进入到点下“锁定” |
| 锁定后二次生成主观一致 | 4 分制 ≥ 3 | 换一页后是否仍像同一产品 |
| Token 一致率 | 主色 / 圆角 / 字体 > 90% | 同一 style_id 再生成 3 个页面 |
| 导出物真实使用率 | 可观测到复制/下载后被粘贴到下游 | 证明交付物有用，不只是看图 |
| 推倒重来率 | 明显低于“直接文生 UI”基线 | 选完后又整轮重生成的比例下降 |
| “好看但不是我想要的”标记率 | 用三问打分追踪 | 区分审美喜欢和需求匹配 |

## 14. 关键产品原则（写进开发备忘）

1. 生成图是决策界面，不是最终交付。
2. 同一 Structure Spec，只扫 Style 轴。
3. 用户挑的是方向，落地用 token。
4. 审美喜欢和需求匹配必须拆开问。
5. 先选 1 个旗舰页定风格，再铺其他页。
6. 没有 Style Spec 的“选图功能”等于没做完。

## 15. 待确认问题（评审时拍板）

产品形态

1. 这是独立工具，还是嵌在现有产品（AI 出码 / 出设计）里的上游模块？
2. 生成对象先做 App UI、官网，还是品牌视觉都要？建议 MVP 只做产品 UI 的旗舰页。
3. 用户选完后下一步是出高保真、出代码，还是只给设计师看？这决定导出格式优先级。

范围与约束

4. 第一期是否只做移动端旗舰页，Web 放到二期？
5. 导出优先对接哪一个下游：Cursor prompt pack、CSS variables，还是 Figma？
6. 有没有必须遵守的品牌资产（色、字体、Logo）？约束模式是否进 MVP？
7. 更在意“候选图好看”，还是“锁定后下一页不漂”？建议以后者为准。

体验细节

8. 生成预览以“可实现的 token 渲染”为主，还是以“更有氛围的生图”为主？建议前者为主、后者为辅。
9. 风格命名用设计术语（Glassmorphism）还是用户口语（通透、高级、像苹果）？建议界面用口语，内部用术语。
10. 多语言：中文产品描述为主，是否要同时支持英文 PRD？
